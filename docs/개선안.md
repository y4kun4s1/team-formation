## 1. 해야 할 것 (효과 큰 순서)

### 1-1. 거절된 지원의 이유를 지원자에게 보여 주기
- 문제: 거절되면 지원자 화면에서 대기 문구만 사라지고 지원 단추가 다시 나온다. 이유를 알 수 없다.
- 변경: `render_my_status`에서 `svc.last_application(me.id)`를 읽어, 팀이 없고 대기 중인 지원이 없으며 마지막 지원이 "거절"이면 `st.warning`으로 "팀N 지원이 거절됨: 이유"를 보여 준다. 새 컨테이너 `my_application`을 쓴다.
- 파일: `streamlit_app.py`
- 테스트: 중간 시나리오 5단계처럼 학생 9가 팀2에 지원하고 팀원이 거부하면 학생 9 화면에 "거절"과 이유가 나온다. 승인된 학생에게는 안 나온다.
- 위험: 낮음. 이유 문구는 DB의 `reason`(규칙 상수)이라 비밀값이 없다.

### 1-2. 관리자 화면에 AI 호출 기록 표 보이기
- 문제: `tf_ai_logs`에 기록은 쌓이지만 화면에는 없다. 5항(AI 실패 사례)의 근거를 얻기 어렵다.
- 변경: `Service.recent_ai_logs(limit=10)`을 추가하고, 관리자 화면에 컨테이너 `ai_logs`로 시각, 모델, 상태, 걸린 시간(초), 이유 요약을 표로 보인다. 기록에는 키와 응답 본문이 없다(`error_summary`는 200자로 잘림).
- 파일: `service.py`, `streamlit_app.py`
- 테스트: 가짜 AI가 실패하는 서비스로 배정한 뒤 최근 기록 3건이 모델 이름과 함께 돌아온다. 화면 테스트에서 `ai_logs`가 보이고 비밀번호 문자열이 없다.
- 위험: 낮음.

### 1-3. "규칙을 지키는 배정이 없음"의 이유를 구체적으로
- 문제: 조합 때문에 불가능한 경우 이유가 "팀 인원과 역할 조건을 한꺼번에 만족하는 조합이 없음"처럼 일반적이다. 공고 2.5절 8항은 팀과 역할을 말하는 이유를 예로 든다.
- 변경: 먼저 `assignment.py`의 `explain_infeasible`을 읽고, 아래 진단을 순서대로 검사해 첫 번째로 걸린 것을 문장으로 돌려준다.
  1. 남은 학생과 현재 팀원의 합으로는 팀 N개를 2~4명으로 채울 수 없음.
  2. 기획자(웹 프로그래머)를 맡을 수 있는 학생 수가 팀 수보다 적음.
  3. 같은 주 역할의 학생 수가 팀 수보다 많음(비둘기집 원리).
  4. 위에 안 걸리면 일반 문장(기존).
- 파일: `assignment.py`, `tests/test_assignment.py`
- 테스트: 위 1~3을 각각 만드는 작은 입력을 만들어 문장에 팀 번호나 역할 이름이 들어 있는지 본다. 기존 시나리오 테스트는 그대로 통과해야 한다.
- 위험: 중간. 진단이 틀리면 안 되므로 "이유가 맞는 경우만" 구체 문장을 쓰고, 확신이 없으면 일반 문장으로 남긴다.

### 1-4. 배정안을 DB에 저장해 새로고침해도 유지
- 문제: 배정안이 관리자의 `session_state`에만 있어, 새로고침하면 사라지고 AI를 다시 불러야 한다(하루 50회 한도 소모).
- 변경: `tf_settings`에 `proposal` 키로 JSON 문자열을 저장한다(스키마 변경 없음). 배정할 때 저장하고, 화면은 저장된 값을 읽고, 확정과 명단 올리기 때 지운다(명단 올리기는 이미 `tf_settings`를 비운다). `confirm`은 이미 `validate_assignment`로 다시 검사한다.
- 파일: `service.py`, `streamlit_app.py`
- 테스트: 배정 → 새 서비스 인스턴스로 읽기 → 같은 배정안. 확정 뒤에는 없음. 상태가 바뀌어 검사를 통과하지 못하면 확정이 막힘.
- 위험: 중간. 저장된 배정안이 낡았을 때 확정이 막히는 경로를 반드시 테스트한다.

### 1-5. 투표 현황 보이기
- 문제: 팀원이 누가 투표하지 않았는지 모르고, 관리자는 대기 중인 지원을 한눈에 볼 수 없다.
- 변경: `pending_votes` 컨테이너의 각 지원에 "투표 2/3명 · 기다리는 사람: 이름"을 보인다. 관리자 화면에는 컨테이너 `pending_overview`로 "지원자 → 팀, n/m 투표" 목록을 둔다. 지원자 이름은 `team_N` 컨테이너 밖에만 둔다.
- 파일: `service.py`(대기 지원 요약 조회), `streamlit_app.py`
- 테스트: 지원 1건과 투표 1건 뒤 숫자가 맞다. `team_N` 텍스트에 지원자 이름이 없다(기존 테스트 유지).
- 위험: 낮음.

### 1-6. 지원 취소
- 문제: 팀원이 투표하지 않으면 지원자는 마감까지 다른 팀에 지원할 수 없다.
- 변경: `Service.cancel_application(student_id)`를 추가한다. 본인의 대기 지원만 "거절(지원자가 취소함)"로 바꾸고, 팀 행 잠금을 건 뒤 처리한다. 화면에는 지원 대기 문구 옆에 `cancel_application` 단추를 둔다. 결과 안내는 "거절: …"로 시작한다.
- 파일: `service.py`, `streamlit_app.py`
- 테스트: 대기 지원이 취소되고 같은 학생이 다른 팀에 지원할 수 있다. 다른 사람의 지원은 취소할 수 없다. 마감 뒤에는 이미 거절됐으므로 막힘.
- 위험: 낮음~중간. 승인 처리와 동시에 일어나는 경우를 팀 잠금으로 막는다.

### 1-7. DB 오류 안내와 문서 맞추기
- `propose_assignment`와 `upload_roster`의 첫 DB 접속을 `try`로 감싸 "잠시 후 다시 시도해 주세요"를 돌려준다.
- `docs/PRD.md` 11절 모델 후보와 테스트 계획(`AppTest` → Playwright)을 실제에 맞게 고치고, `key.env` 결정과 `Student.is_admin`, 서비스의 조회 함수를 `docs/구현 계획.md`에 반영한다.

## 2. 시간이 남으면 (선택)

- **갱신 질의 줄이기**: 한 번의 갱신에 쓰는 DB 연결을 하나로 묶는 조회 함수(`snapshot`)를 만든다. 갱신 간격은 공고의 5초 이하 안에서 유지한다. 동시 접속 부하는 직접 시험하지 못했으므로 효과는 추정이다.
- **GitHub Actions에서 테스트 돌리기**: PostgreSQL 서비스 컨테이너로 `pytest`를 돌리는 워크플로를 추가한다. 보호된 폴더라 직접 옮겨야 하고, 11/2 이후에는 push하지 않는다.
- **관리자 화면의 `whoami`**: "관리자 (관리자)" 중복 표기를 정리한다.
