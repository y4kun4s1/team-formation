# 화면 갱신 개선 설계 (접근 A: 변경 감지 + 스냅샷)

작성일 2026-10-31 · 상태: 검토 대기

## 1. 해결할 문제

3초마다 화면 전체를 다시 그리고 DB도 매번 다시 읽는다. 그 결과 사용자가 겪는 증상은 세 가지다.

- 화면 깜빡임: 바뀐 게 없어도 다시 그려진다.
- 클릭·입력이 씹힘: 갱신이 도는 중에 누른 클릭이 버려진다.
- 계속 로딩 중: DB가 느리면 갱신이 다음 갱신과 겹친다.
- 흐려진 채 굳음(스크린샷): Streamlit은 다시 그리는 동안 이전 요소를 흐리게(stale) 표시한다. 갱신이 끝나지 않거나 겹치면 이 흐린 상태가 풀리지 않고, 새 내용과 옛 내용이 섞여 쌓여 보인다. 같은 원인(3초마다 본문 전체 재실행)에서 나오므로 3-2의 "변경이 없으면 다시 그리지 않음"이 1차 해결책이다.

배포 사이트의 브라우저 콘솔(스크린샷)에는 `/api/v2/user/details` 404가 계속 쌓이고, 중간에 `WebSocket onclose code=1006`(비정상 종료) 경고가 있었다. 앞의 것은 우리 코드에 없는 경로라서 Streamlit 호스팅 쪽 요청으로 보이며(제 추정), 앱에서 고칠 수 없고 기능에도 영향이 없다. 뒤의 것은 서버와의 연결이 갑자기 끊겼다는 뜻이다. 서버가 느린 갱신에 묶여 응답하지 못할 때 생길 수 있고, 연결이 끊겼다 다시 붙는 동안 화면이 흐린 채 멈춘다. 그래서 서버 부하를 줄이는 이 설계가 1차 대응이다. 호스팅 쪽 원인(메모리 초과로 재시작 등)은 Streamlit의 앱 관리 화면 로그로 따로 확인한다.

측정값: 한 번 갱신에 DB 왕복이 학생 15회, 관리자 28회(연결 검사 포함). 왕복 한 번이 200ms면 사용자 1명이 연결 1개를 거의 계속 점유해서, 약 5명이면 연결 풀(5개)이 가득 찬다.

## 2. 목표와 성공 기준

| 기준 | 값 |
|---|---|
| 다른 사람이 바꾼 내용이 내 화면에 보이기까지 | 5초 이하 (DB 왕복 100~200ms 가정) |
| 아무도 안 바꾼 동안 화면 | 10초간 DOM 변화 없음 (깜빡임 0) |
| 변경이 멈춘 뒤 화면 | 5초 안에 흐린(stale) 요소 0개, 중복 요소 0개 |
| 변경 확인(폴링) 1회의 DB 질의 | 1개, 여러 사용자가 공유하면 초당 약 1개 |
| 변경이 있을 때 화면 하나를 그리는 DB 왕복 | 학생 약 8회, 관리자 약 10회 이하 |
| 2~4초 간격의 사람 속도 클릭 | 씹히지 않음 |

범위 밖: 스키마 변경, WebSocket 등 새 인프라, 기능 추가. 학생/관리자 화면의 모양과 위젯 key는 그대로 둔다.

## 3. 설계

### 3-1. 변경 토큰 `Service.change_token()`

질의 한 번으로 "지금 DB 상태의 지문"을 문자열로 돌려준다. 다음을 합쳐 해시한다.

- `tf_members`: (team_id, slot_no, student_id) 전체
- `tf_applications`: (id, status) 전체
- `tf_votes`: 행 수와 최대 id
- `tf_settings`: `closed` 값
- `tf_students` 행 수, `tf_teams` 행 수
- `tf_ai_logs`: 최대 id

읽기만 하고 스키마는 바꾸지 않는다. 위 데이터 중 하나라도 쓰기가 일어나면 토큰이 바뀐다.

### 3-2. 감시자와 화면 전환

- 눈에 안 보이는 감시자 fragment(`run_every=2초`)가 토큰을 읽는다. 토큰은 `st.cache_data(ttl=1)`로 모든 세션이 공유하므로 사용자가 많아도 DB 질의는 초당 약 1개다.
- 세션의 `seen_token`과 다르면 `st.rerun()`(앱 전체)으로 화면을 다시 그린다. 같으면 아무것도 하지 않는다.
- 본문은 더 이상 `run_every` fragment 안에 있지 않다. 그래서 변경이 없으면 화면이 전혀 다시 그려지지 않는다.
- 내가 버튼을 눌러 쓰기를 한 경우(`finish()`)는 곧바로 `st.rerun()`으로 내 화면을 갱신한다.
- 안내 문구는 "마지막 갱신"을 "마지막 변경 반영: HH:MM:SS (한국 시각)"으로 바꾼다.
- 최악의 지연: 토큰 캐시 1초 + 폴링 2초 + 그리기 시간 ≈ 3~4초 (< 5초).

### 3-3. 스냅샷 `Service.snapshot(student_id)`

한 번의 렌더에 필요한 데이터를 연결 하나로 한꺼번에 읽는다.

- 공통(모두 같은 데이터): 팀 목록(팀·멤버·역할을 조인 질의 하나로), 마감 여부. 토큰을 키로 `st.cache_data`에 두어 같은 변경에 대해 모든 세션이 한 번만 읽는다.
- 학생 전용: 내 정보, 내 대기 신청, 마지막 신청, 내 팀의 대기 신청, 내 투표.
- 관리자 전용: 미배정 학생, AI 기록.
- 기존 개별 getter(`get_student`, `teams`, …)는 그대로 둔다. 스냅샷 결과가 개별 getter와 같음을 테스트로 확인한다.
- 학생 화면과 관리자 화면을 그리는 함수는 분리된 스냅샷을 받아 그리고, 렌더 중에는 DB를 다시 읽지 않는다.

### 3-4. 오류 처리

- DB 접속 실패: 기존 문구 "DB에 접속하지 못했어요. 잠시 후 자동으로 다시 시도해요."를 보여 주고 `seen_token=None`으로 둔다. 감시자가 계속 돌다가 복구되면 토큰이 달라져 자동으로 다시 그린다.
- 내 학생 정보가 사라진 경우(`me is None`): 기존처럼 세션을 비우고 로그인 화면으로 간다.
- 토큰 질의만 실패해도 화면은 그대로 두고 다음 폴링에서 다시 시도한다.

## 4. 테스트

1. 토큰 단위 테스트(실제 PostgreSQL): 신청, 투표 승인·거절, 마감, 명단 업로드, 배정 확정, AI 기록이 각각 토큰을 바꾸고, 읽기만 하면 바뀌지 않는다.
2. 스냅샷 단위 테스트: 학생·관리자 스냅샷이 기존 개별 getter 결과와 같다.
3. 질의 수 회귀 테스트: 폴링 1회 = 질의 1개, 렌더 1회 = 정한 상한 이하.
4. 브라우저(Playwright) 수용 테스트
   - 변경이 없는 10초 동안 DOM이 바뀌지 않는다.
   - 임시 지연 프록시로 DB에 100~200ms 지연을 넣은 상태에서 다른 사용자의 변경이 5초 안에 보인다. (지연은 시험 도구에만 두고 제품 코드에는 넣지 않는다.)
   - 2~4초 간격의 사람 속도 클릭이 씹히지 않는다.
   - 흐림·누적 검사: 지연을 넣은 상태에서 변경을 여러 번 일으킨 뒤, 변경이 멈춘 5초 안에 `data-stale="true"` 요소가 0개가 되고, 같은 key의 요소(팀 카드, 지원 카드 등)가 중복 없이 한 개씩만 있다.
5. 기존 전체 테스트와 `scripts/audit.py` 통과.

## 5. 위험과 대응

- 토큰이 놓치는 변경: 위 목록 밖의 표를 쓰는 기능이 생기면 토큰에 추가해야 한다. 토큰에 들어가는 표를 한 곳(함수 하나)에 모아 두고 테스트로 고정한다.
- 변경 직후 여러 세션이 동시에 읽는 폭주: 토큰 키 공유 캐시로 공통 데이터는 한 번만 읽는다.
- `st.rerun()` 중 사용자가 타이핑 중인 값: 입력값은 위젯 key로 세션에 유지되고, 변경이 있을 때만 다시 그려지므로 기존 "입력 유지" 테스트(`test_typed_team_count_survives_refresh`)로 확인한다.

## 6. 작업 순서 (커밋 3개)

1. `change_token()` + 단위 테스트
2. `snapshot()` + 단위 테스트 + 질의 수 회귀 테스트
3. `streamlit_app.py` 화면 전환(감시자, 학생/관리자 분리) + 브라우저 수용 테스트 + README 문제점 4 추가
